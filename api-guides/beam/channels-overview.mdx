The Channels API is the local API of an MK.IO Beam device. It presents everything the device is doing as a number of _channels_, where one channel can cover the input, the processing, and the output of a single service. It is the API behind the Beam Essentials UI, and it runs on the device itself rather than in the MK.IO cloud.

<Warning>
The Channels API requires an MK.IO Beam device running version `1.12.0` or higher. It is delivered as part of the Beam Essentials UI release — devices on earlier versions do not serve these endpoints.
</Warning>

## API overview

| Detail | Value |
| :-- | :-- |
| Base path | `<DEVICE_ADDRESS>/api/` |
| Scope | A single Beam device |
| Access | Network access to the device |

The base URL is the device itself, not `app.mk.io`, and requests go to it over HTTP. The other MK.IO APIs are project-scoped and bearer authenticated against the cloud, so if you already integrate with the Media or Fleets API, treat this as a separate integration.

## How the main resources connect

The API exposes a handful of resource types, and channels are the centre of all of them:

    Holds a `spec` (the configuration you send) and a `status` (what the device reports back).
  </Card>
  <Card title="Interfaces" icon="network-wired">
    The physical and network ports available on the device. Read them to fill in the `interface` and `url` fields of a channel.
  </Card>
  <Card title="Channel Alarms" icon="bell">

  </Card>
  <Card title="Metrics & System" icon="chart-line">
    Describe the device rather than any one channel.
  </Card>
</CardGroup>

A typical integration reads the interfaces once, creates channels against them, then polls channel status and alarms to drive a dashboard or an alerting rule.

## Device address and connection

The base URL for all Channels API requests is built from the device's local network address:

```
http://<DEVICE_ADDRESS>/api/
```

Replace `<DEVICE_ADDRESS>` with the IP address or hostname of your Beam device on your local network. The device serves a Swagger UI page that you can use to browse available endpoints and try requests interactively.

Unlike the cloud APIs, the Channels API does not use bearer token authentication against the MK.IO cloud. Access is controlled by network reachability to the device. Ensure your client has appropriate network access to the device before making requests.

## Common workflow patterns

Follow this sequence when automating a Beam device:

<Steps>
  <Step title="Connect and confirm the version">
    Verify the device is reachable and confirm it reports version `1.12.0` or higher before issuing any channel operations.
  </Step>

  <Step title="Read the available interfaces">
    Query the interfaces endpoint to discover which physical and logical ports the device exposes:

    ```bash
    curl -X GET "http://<DEVICE_ADDRESS>/api/interfaces"
    ```

    The returned interface names and types are what you use when filling in the `interface` and `url` fields on a channel spec.
  </Step>

  <Step title="Create and start a channel">
    Create a channel by POSTing a spec that names the input, processing, and output configuration. The response returns the channel identifier you use for subsequent reads and updates.

    ```bash
    curl -X POST "http://<DEVICE_ADDRESS>/api/channels" \
      -H "Content-Type: application/json" \
      -d '{
        "spec": {
          "displayName": "Studio Feed",
          "input": { ... },
          "output": { ... }
        }
      }'
    ```

    The device applies the configuration asynchronously. Poll the channel's status until it reflects the desired state.
  </Step>

  <Step title="Poll status, health, and alarms">
    Retrieve the channel to check `status`:

    ```bash
    curl -X GET "http://<DEVICE_ADDRESS>/api/channels/<CHANNEL_ID>"
    ```

    List active alarms for a specific channel:

    ```bash
    curl -X GET "http://<DEVICE_ADDRESS>/api/channels/<CHANNEL_ID>/alarms"
    ```

    Query device-level metrics and system information:

    ```bash
    curl -X GET "http://<DEVICE_ADDRESS>/api/metrics"
    curl -X GET "http://<DEVICE_ADDRESS>/api/system"
    ```
  </Step>
</Steps>

## Key operations

<Accordion title="List channels">
  Retrieve all channels configured on the device:

  ```bash
  curl -X GET "http://<DEVICE_ADDRESS>/api/channels"
  ```

  The response lists every channel with its `spec` and current `status`.
</Accordion>

<Accordion title="Update a channel">
  Send a PUT or PATCH to update an existing channel's configuration. Configuration changes are applied asynchronously on the device, so poll the status after updating.
</Accordion>

<Accordion title="Delete a channel">
  ```bash
  curl -X DELETE "http://<DEVICE_ADDRESS>/api/channels/<CHANNEL_ID>"
  ```
</Accordion>

<Accordion title="Import and export channels">
  Move a channel configuration between devices or restore one after a rebuild. The import and export endpoints accept and produce channel configuration bundles.
</Accordion>
