MK.IO webhooks let your application receive real-time notifications when platform events occur, such as a transcoding job finishing or a live event changing state. Each webhook rule is project-scoped, identified by a stable name, and delivers payloads in the CloudEvents format to an HTTPS endpoint you control. MK.IO retries failed deliveries automatically.

Webhooks launched in all regions at no additional cost.

## Create or update a webhook rule

Create or replace a rule with `PUT` at its name. The `spec` requires `enabled`, `url`, and `events`. Put secrets in `authentication.headers` or `authentication.queryParams` (these are write-only and read back masked). Put non-sensitive decoration in the top-level `headers` and `queryParams`.

```bash
curl -X PUT "https://app.mk.io/api/v1/projects/$MKIO_PROJECT/webhook/rules/job-notifications" \
  -H "Authorization: Bearer $MKIO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "spec": {
      "url": "https://your-endpoint.example.com/webhook",
      "enabled": true,
      "events": ["MediaKind.JobStarted", "MediaKind.JobFinished"],
      "authentication": {
        "headers": { "X-Webhook-Secret": "<SHARED_SECRET>" }
      },
      "headers": { "X-Source": "mkio" }
    }
  }'
```

Because `PUT` replaces the whole rule, include the full `spec` each time. To pause delivery without losing the rule, send the same `PUT` with `enabled` set to `false`.

## Supported events

MK.IO delivers notifications for the following event types:

| Event | Trigger |
| --- | --- |
| `MediaKind.JobStarted` | A processing job begins execution |
| `MediaKind.JobFinished` | A processing job completes successfully |
| `MediaKind.JobErrored` | A processing job fails |
| `MediaKind.ChannelInstanceStarted` | A live event or channel starts |
| `MediaKind.ChannelInstanceStopped` | A live event or channel stops |
| `MediaKind.ChannelInstanceError` | A live event or channel encounters an error |

## Read the rule

Authentication values read back masked, so use the read response to confirm the structure, enabled state, URL, events list, and non-secret headers.

```bash
# List all rules in a project
curl -X GET "https://app.mk.io/api/v1/projects/$MKIO_PROJECT/webhook/rules" \
  -H "Authorization: Bearer $MKIO_TOKEN"

# Read a specific rule
curl -X GET "https://app.mk.io/api/v1/projects/$MKIO_PROJECT/webhook/rules/job-notifications" \
  -H "Authorization: Bearer $MKIO_TOKEN"
```

## Inspect delivery history

When your application reports a missing event, the rule's `events` collection is the first place to look:

```bash
curl -X GET "https://app.mk.io/api/v1/projects/$MKIO_PROJECT/webhook/rules/job-notifications/events" \
  -H "Authorization: Bearer $MKIO_TOKEN"
```

Each record carries `created`, `source`, `type`, and a `status` of `Pending`, `Retrying`, `Failed`, or `Sent`. A `Failed` or stuck `Retrying` status points at the receiving endpoint rather than MK.IO.

## Delete a rule

```bash
curl -X DELETE "https://app.mk.io/api/v1/projects/$MKIO_PROJECT/webhook/rules/job-notifications" \
  -H "Authorization: Bearer $MKIO_TOKEN"
```

<Warning>
Deleting a rule also removes its event history. Export anything you need for debugging or audit purposes before deleting.
</Warning>

## Common issues

<Accordion title="A PUT drops fields you forgot to include">
  `PUT` replaces the entire `spec`. Read the rule, change what you need, and send the complete spec back.
</Accordion>

<Accordion title="Secrets look wrong on read">
  Authentication values are write-only and read back masked. That is expected behavior — they are still sent on delivery.
</Accordion>

<Accordion title="Events never arrive">
  Check the `/events` history. A `Failed` status means your endpoint rejected the delivery. Verify it is reachable over HTTPS and returns a `2xx` success response. Your handler must respond quickly — a slow response may trigger a timeout and retry.
</Accordion>

## Set up your webhook handler

Your HTTP endpoint must:

- Be reachable over public HTTPS
- Accept `POST` requests with a `Content-Type: application/json` body
- Return a `2xx` HTTP status code within a reasonable timeout

Validate the shared secret in the request headers to confirm that deliveries originate from MK.IO. Process the event asynchronously when possible — return a `200 OK` immediately and handle the payload in a background worker to avoid timeout retries.
