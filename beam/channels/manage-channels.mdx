Channels are created with `PUT /api/channels/{channel_id}/`, where `{channel_id}` is the channel name you choose. The same request creates a channel that does not exist and replaces one that does, so there is no separate create endpoint and no generated identifier to keep track of.

Read [How Channels Work](/beam/channels/how-channels-work) first if you have not picked a `spec.type` yet, because that choice constrains everything else in the body.

## Read the Interfaces First

Channel inputs and outputs point at real ports on the device, so start by asking the device what it has:

```bash
curl <BASE_URL>/api/interfaces/
```

The response groups interfaces by kind. This is a response from a VEGA-7010, abbreviated to the first two of its four slot ports:

```json
{
  "ip": [
    { "name": "lo", "type": "IP", "ipAddresses": ["127.0.0.1"], "displayName": "lo" },
    { "name": "eth0", "type": "IP", "ipAddresses": ["10.0.0.10"], "displayName": "eth0" },
    { "name": "eth1", "type": "IP", "ipAddresses": ["172.16.0.10"], "displayName": "eth1" }
  ],
  "sdi": [
    {
      "name": "slot_1_port_1",
      "type": "SDIASI",
      "url": "sdi://localhost/slot_1_port_1",
      "displayName": "Slot 1 / Port 1"
    },
    {
      "name": "slot_1_port_2",
      "type": "SDIASI",
      "url": "sdi://localhost/slot_1_port_2",
      "displayName": "Slot 1 / Port 2"
    }
  ],
  "asi": [
    {
      "name": "slot_1_port_1",
      "type": "SDIASI",
      "url": "asi://localhost/slot_1_port_1",
      "displayName": "Slot 1 / Port 1"
    },
    {
      "name": "slot_1_port_2",
      "type": "SDIASI",
      "url": "asi://localhost/slot_1_port_2",
      "displayName": "Slot 1 / Port 2"
    }
  ],
  "rf_demod": [],
  "rf_modulator": [],
  "st2110": []
}
```

The groups are `ip`, `sdi`, `asi`, `rf_demod`, `rf_modulator`, `cam`, and `st2110`. Every one defaults to an empty array, so what a device returns depends entirely on the hardware fitted to it.

Network transports take an interface `name`, such as `eth0`. Baseband and RF transports take the `url` exactly as returned.

<Warning>
  Copy the `url` rather than composing it. The same physical port is listed under both `sdi` and `asi` with the same `name`, and only the scheme in the `url` distinguishes them. A `name` on its own does not identify a port.
</Warning>

## Create a Channel

This request creates a contribution channel that takes an SDI source, encodes it, and publishes it as an SRT listener. It is created stopped, so nothing goes on air until you ask it to.

```bash
curl -X PUT <BASE_URL>/api/channels/news-contribution/ \
  -H "Content-Type: application/json" \
  -d '{
    "kind": "BeamChannel",
    "metadata": {
      "name": "news-contribution",
      "displayName": "News contribution"
    },
    "spec": {
      "type": "EncodingContribution",
      "state": "Stopped",
      "inputs": [
        {
          "type": "SDI",
          "name": "sdi-in",
          "transport": { "url": "sdi://localhost/slot_1_port_1" }
        }
      ],
      "transform": {
        "encoding": {
          "video": {
            "codec": "H264High",
            "videoFormat": "1920x1080p",
            "bitrate": 15000000
          },
          "audios": [
            { "codec": "AC3", "mode": "Stereo", "bitrate": 128000 }
          ]
        }
      },
      "outputs": [
        {
          "type": "SRTListener",
          "transport": { "interface": "eth0", "port": 9000 }
        }
      ]
    }
  }'
```

Fields that are easy to get wrong:

- Set `metadata.name` to the same value as `{channel_id}` in the path. It cannot be changed afterwards. Use a readable slug such as `news-contribution` rather than a generated identifier.
- Each entry in `inputs` needs its own `name`. Audio entries in `transform.encoding.audios` refer back to inputs through `inputName`.
- `bitrate` is in bits per second and accepts `100000` to `60000000`.
- `port` on an SRT listener accepts `256` to `65535`.
- Outputs take no `name`, unlike inputs (the exception is ASI, where `name` is optional).

Confirm the result by reading `status.syncState`:

```bash
curl <BASE_URL>/api/channels/news-contribution/
```

Read `status.syncState`. It reports `Configuring` while the device applies the change and `Ok` once the running configuration matches your spec. Anything else means the configuration was accepted but could not be applied, and `status.syncError` carries the detail.

## Choosing Between Channel Types

| Your situation | `spec.type` | Body differences |
| :-- | :-- | :-- |
| Encoding a baseband source for onward contribution | `EncodingContribution` | Requires `transform.encoding`. Video codecs include 4:2:2 and JPEG XS profiles plus `H264High`. |
| Encoding a baseband source for delivery to viewers | `EncodingDistribution` | Requires `transform.encoding`. Video codecs: `HEVCMain`, `HEVCMain10bit`, `H264High`, `H264Main`, `MPEG2`. |
| Encoding a baseband source into adaptive bitrate output | `EncodingStreaming` | Requires `transform.abrEncoding` instead. The only output type is `HttpStreaming`. |
| Receiving a stream and putting it back to baseband | `ReceptionDecoding` | No `transform`. Outputs are `SDI` or `Smpte2110`. |
| Receiving a stream and passing it on untouched | `ReceptionGateway` | No `transform`. Outputs are the transport types, as for contribution. |

A reception channel is considerably shorter, because there is nothing to encode. This example takes a multicast UDP source and decodes it out of an SDI port, and starts immediately:

```bash
curl -X PUT <BASE_URL>/api/channels/udp-to-sdi/ \
  -H "Content-Type: application/json" \
  -d '{
    "kind": "BeamChannel",
    "metadata": {
      "name": "udp-to-sdi",
      "displayName": "UDP to SDI decoder"
    },
    "spec": {
      "type": "ReceptionDecoding",
      "state": "Running",
      "inputs": [
        {
          "type": "UDP",
          "name": "udp-in",
          "transport": {
            "url": "udp://239.100.1.1:5001",
            "interface": "eth0"
          }
        }
      ],
      "outputs": [
        {
          "type": "SDI",
          "transport": { "url": "sdi://localhost/slot_1_port_1" }
        }
      ]
    }
  }'
```

A UDP input needs both a `url` and an `interface`, because the device must know which network port to receive the stream on. Addresses in the class D range (`224.0.0.0/4`) are treated as multicast, and anything outside that range is treated as unicast.

### Encrypting an SRT Output

To encrypt an SRT output, set `encryptionStandard` to `AES128`, `AES192`, or `AES256`, and supply a passphrase of at least 10 characters:

```json
{
  "type": "SRTListener",
  "transport": {
    "interface": "eth0",
    "port": 9000,
    "encryptionStandard": "AES128",
    "passPhrase": "<PASSPHRASE>"
  }
}
```

`passPhrase` is optional when `encryptionStandard` is `None` (the default) and required as soon as it is set to anything else. A passphrase shorter than 10 characters is rejected.

## Start, Stop, and Rename

`PATCH /api/channels/{channel_id}/` handles the two changes you make most often. It accepts only the desired state and the display name, so use `PUT` for anything else.

Start a channel:

```bash
curl -X PATCH <BASE_URL>/api/channels/news-contribution/ \
  -H "Content-Type: application/json" \
  -d '{ "spec": { "state": "Running" } }'
```

Stop a channel by sending `"Stopped"` in the same shape. Rename it with:

```bash
curl -X PATCH <BASE_URL>/api/channels/news-contribution/ \
  -H "Content-Type: application/json" \
  -d '{ "metadata": { "displayName": "News contribution, main feed" } }'
```

Renaming changes `displayName` only. `metadata.name` is fixed for the life of the channel — a channel that needs a different identifier must be recreated.

## Delete a Channel

```bash
curl -X DELETE <BASE_URL>/api/channels/news-contribution/
```

A successful delete returns `204` with no body. The device stops the underlying services before removing the channel.

## What Goes Wrong

<Accordion title="The request succeeded but nothing is on air.">
  Check `spec.state`. A channel created with `"state": "Stopped"` stays stopped until you patch it. If the state is `Running`, check `status.syncState` and `status.syncError`.
</Accordion>

<Accordion title="A codec value is rejected.">
  The accepted video codecs depend on `spec.type`. `HEVCMain` is valid for `EncodingDistribution` and `EncodingStreaming` but not for `EncodingContribution`, which takes the 4:2:2 profiles. The accepted `videoFormat` values depend on the codec you chose, and interlaced formats are not available with progressive-only codecs such as JPEG XS.
</Accordion>

<Accordion title="An audio bitrate is rejected.">
  Audio bitrate is constrained by codec and mode together. `AC3` with `Stereo` starts at `96000`, while `AC3` with `Surround51` starts at `224000`.
</Accordion>

<Accordion title="A PUT removed settings you did not send.">
  `PUT` replaces the channel rather than merging into it. Fetch the channel, change what you need in the returned `spec`, and send the whole `spec` back.
</Accordion>

<Accordion title="The response is 422.">
  The body contains a `detail` array, and each entry has a `loc` array giving the exact path to the offending field. Read `loc` before anything else, because it points straight at the field name.
</Accordion>

<Accordion title="The response is 503.">
  The channel endpoints return `503` when the API cannot serve the request. Retry, and if it persists, check the device itself.
</Accordion>
